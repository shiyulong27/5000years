# 上下五千年 · 历史时间线 —— 设计文档

日期：2026-08-04
状态：已确认

## 一、项目目标

建立一个从上古到 2026 年的中国历史事件时间线，供作者本人阅读与学习。世界史作为副线对照呈现。

内容由 AI 生成初稿、作者审校修订，长期持续完善。因此设计的首要目标是：**降低添加与修订一条事件的成本**。工具部分数日可成，内容部分是长期工程；工具的价值在于让内容工程能持续下去。

## 二、核心决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 内容来源 | AI 生成初稿，作者审校 | 快速获得可读内容；审校过程本身即学习 |
| 内容范围 | 中国史为主线（详），世界史为副线（略） | 「孔子与释迦牟尼几乎同时」这类认知需要对照才能浮现 |
| 使用设备 | 桌面 + 手机（响应式网页） | 桌面深读与编辑，手机随手翻阅 |
| 展示形态 | 三栏对照长卷 + 朝代概览页 | 长卷保连续感，卡片保结构感 |
| 技术栈 | Astro 静态站点 + GitHub Pages | 构建时渲染，万条数据仍秒开；push 即发布 |
| 数据格式 | YAML，按朝代分文件 | 手改友好，git diff 清晰 |
| 第一版范围 | 全时段骨架 + 抗战高密度样本 | 先打通五千年形状，再逐段填充 |

**贯穿全局的原则：内容与展示彻底分离。** `data/` 是纯 YAML，不依赖任何前端代码。展示层可以重写十次，数据一行不动。这是项目能长期存续的前提。

## 三、展示设计

### 3.1 长卷主页（`/`）

三栏布局，从最早时期滚动至 2026：

```
+-----------------+----------+------------------+
|    同期世界      |   年代    |      中国         |
+-----------------+----------+------------------+
| | 古埃及新王国   |  前221   | 秦灭六国，统一中国 |
| | (文明色带)     | [秦始皇] |                  |
|                 |  ######  |                  |
|   汉尼拔翻越     |  前213   | 焚书坑儒          |
|   阿尔卑斯山     |  ######  |                  |
+-----------------+----------+------------------+
        左栏            中轴           右栏
                 年份+朝代色带+在位君主
```

**中轴承载三重信息**：年份、朝代色带（背景色）、当年在位君主。左右两栏因此保持纯净，只放事件卡片。

**朝代横幅**横跨三栏，在朝代切换处插入，含：朝代名、起止年、共多少年、都城、君主 chip 列表（开国者白底高亮、末代深色标记）。

**顶部工具栏**：朝代快速跳转 chips + 三个开关。
- 同期世界对照（默认开）—— 关闭时中轴左移、中国栏占满
- 只看重大事件 —— 按 `importance` 过滤
- 分类筛选 —— 政治/战争/文化/科技/经济/外交/灾异

**世界栏的文明色带**：跨越数百年的纵向色带（如「古埃及新王国 前1550–前1069」「罗马共和国 前509–前27」），填充世界事件稀疏处的空白。这既避免了「空白 = 当时外国没发生事」的误读，也让世界栏从零散事件升级为文明演进图。

**响应式**：手机上三栏放不下，降为两栏（中轴 + 中国），世界事件折叠为中国事件卡片下方的可展开小条。

### 3.2 朝代概览页（`/dynasty/[id]`）

供「查」而非「读」，与长卷互补。内容自上而下：

1. **统计数字**（全部自动计算）：享国年数、历任君主数、最长在位者、已收录事件数
2. **一句话概述**（`summary` 字段，留空则不渲染）
3. **关键节点**：自动取 `importance ≥ 4` 的事件，点击跳回长卷对应位置
4. **同期世界**：该朝代时段内的文明色带
5. **完整世系表**：庙号/称号、姓名、在位起止、在位年数、备注

设计要点：**结构完整，内容可增量填充**。第一版不写任何概述文字，页面依然是一份像样的自动生成概览。作者何时想为某朝代写概述，填入 `summary` 即可。

## 四、数据模型

### 4.1 目录结构

```
data/
├── dynasties.yaml           朝代定义
├── rulers/                  统治者世系，按朝代分文件
│   ├── qin.yaml
│   └── han.yaml
├── events/                  中国事件，按朝代分文件
│   ├── qin.yaml
│   └── modern-1931-1945.yaml
├── world/                   世界事件
│   └── ancient.yaml
└── civilizations.yaml       文明色带
```

**文件命名规则**：`events/` 与 `rulers/` 下的文件名不参与解析，仅供人工归档之便——事件归属哪个朝代由其 `date` 与 `dynasties.yaml` 的区间比对决定，而非由文件名决定。因此近现代等不便按朝代切分的时段，可自由采用 `modern-1931-1945.yaml` 这类按年代命名的文件。

### 4.2 事件（Event）

```yaml
- id: qin-unify-221bc
  date: "-0221"
  title: 秦灭六国，统一中国
  category: 政治
  importance: 5
  summary: |
    秦王政灭齐，天下一统，自称始皇帝。废分封行郡县，
    书同文、车同轨、统一度量衡，中央集权制度自此确立。
  confidence: 确定
  sources: [史记·秦始皇本纪]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一，用于锚点链接与交叉引用 |
| `date` | 是 | 字符串，变精度。见下 |
| `title` | 是 | 事件标题 |
| `category` | 是 | 政治/战争/文化/科技/经济/外交/灾异 |
| `importance` | 是 | 1–5 |
| `summary` | 否 | 简述，数行以内 |
| `confidence` | 否 | 确定/存疑/有争议，默认「确定」 |
| `sources` | 否 | 出处列表 |
| `figures` | 否 | 相关人物，为未来人物页预留 |
| `location` | 否 | 地点，为未来地图预留 |
| `detail` | 否 | 指向 Markdown 长文的相对路径 |

**`date` 为字符串而非日期类型，这是刻意的**。采用 ISO 8601 扩展格式，负号表示公元前，支持三种精度：

- `"-0221"` —— 仅到年（公元前 221 年）
- `"-0209-07"` —— 到月
- `"1937-07-07"` —— 到日

变精度是刚需：夏商只能确定到「约公元前 1600 年」，抗战需精确到日。使用日期类型会强迫为未知的月、日编造数值。

**`confidence` 直接服务于「AI 生成、人工审校」的工作方式**。AI 在冷门年代与精确日期上会出错，此字段让作者一眼识别需要核查的条目。夏商周断代本属学界争议，此字段亦为必需。

**`importance` 一字两用**：驱动「只看重大事件」开关，同时让朝代概览页自动挑选关键节点。

### 4.3 朝代（Dynasty）

```yaml
- id: qin
  name: 秦
  start: "-0221"
  end: "-0207"
  capital: 咸阳
  color: "#c0392b"
  summary: ""
  parent: null
  concurrent: false
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | 是 | 全局唯一 |
| `name` | 是 | 朝代名 |
| `start` / `end` | 是 | 起止年，格式同 `date` |
| `capital` | 否 | 都城 |
| `color` | 是 | 中轴色带与横幅底色 |
| `summary` | 否 | 概述，留空则概览页不渲染该块 |
| `parent` | 否 | 父朝代 id，默认 null |
| `concurrent` | 否 | 是否为并存政权，默认 false |

**`parent` 字段处理子朝代关系**：西汉/新/东汉的 parent 为 `han`，北宋/南宋的 parent 为 `song`。长卷显示合并后的「汉 前202–220 共422年」，概览页内再拆分展示。若无此层级，顶部导航栏将被数十个碎片填满。

**并存政权**：三国、南北朝、五代十国等分裂期，同一时段存在多个朝代记录（wei/shu/wu）。此类记录须显式声明 `concurrent: true`，否则将被时间重叠校验拒绝。长卷的朝代色带在此处分叉显示。这是数据模型中唯一真正复杂之处，但无法回避——中国史约四分之一时间处于分裂状态。

### 4.4 统治者（Ruler）

```yaml
- dynasty: qin
  temple_name: 秦始皇
  name: 嬴政
  reign_start: "-0221"
  reign_end: "-0210"
  era_names: []
  note: 首称皇帝
  role: founder
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `dynasty` | 是 | 所属朝代 id |
| `temple_name` | 是 | 庙号；无庙号时期存放相应称号 |
| `name` | 否 | 姓名 |
| `reign_start` / `reign_end` | 是 | 在位起止 |
| `era_names` | 否 | 年号列表，汉武帝起才有 |
| `note` | 否 | 备注 |
| `role` | 否 | `founder` / `last` / 空 |

**字段命名为 `ruler` 而非 `emperor`**：夏商周称王，春秋战国为诸侯，民国为总统/委员长，新中国为主席/总书记。写死「皇帝」将在这些时期失效。`temple_name` 在无庙号的时期存放相应称号。

`role` 取值 `founder` / `last` / 空，用于横幅中的开国、末代标记。

### 4.5 文明色带（Civilization）

```yaml
- name: 古埃及新王国
  start: "-1550"
  end: "-1069"
  region: 埃及
  color: "#d4a574"
```

`region` 用于世界栏内的横向分列——同一时段可能有埃及、地中海、印度等多条色带并行，按 region 分配列位。

### 4.6 数据校验规则

`scripts/validate.mjs` 检查：

- 日期格式合法
- 事件日期落在所属朝代区间内
- 朝代时间不重叠（`concurrent: true` 的并存政权除外）
- 君主在位期互不重叠，且落在所属朝代区间内（并存政权内各自独立计算）
- `id` 全局唯一
- 必填字段齐全
- `category` / `confidence` / `importance` 取值在枚举范围内

**区间约定**：朝代与在位期均为**左闭右闭**，交替之年由前后两条记录共享。秦始皇 `-0221~-0210` 与秦二世 `-0210~-0207` 在 -0210 年交接，不算重叠。校验器仅在区间真正交叉（后者起始早于前者结束之年）时报错。

**年数计算**：不存在公元 0 年，故跨越公元前后时年数为 `|start| + end`。汉「前202–220」计为 422 年，与传统纪年习惯一致。

**报错须指向具体文件与行号：**

```
✗ data/events/han.yaml:47
  事件「张骞出使西域」缺少必填字段 importance

✗ data/rulers/qin.yaml:12
  秦二世 在位 -0211~-0207 与 秦始皇 -0221~-0210 重叠
```

作者将大量手工修改数据，报错信息的质量直接决定使用体验。

### 5.1 `timeline.js` —— 唯一的复杂逻辑层

```
输入：events[] + worldEvents[] + dynasties[] + rulers[] + civilizations[]
输出：rows[] —— { year, dynasty, ruler, cnEvents[], worldEvents[], banner? }
```

职责：按年份对齐左右两栏、判定每年所属朝代与在位君主、在朝代切换处插入横幅、计算文明色带的跨行范围。

**独立抽出的理由**：这是纯函数——输入数据、输出数据，不接触 DOM、不依赖 Astro。因此可独立测试，且更换前端框架时可直接复用。组件只负责渲染，不参与计算。

### 5.2 组件职责

| 组件 | 职责 | 输入 |
|---|---|---|
| `Timeline` | 三栏骨架、滚动、吸顶 | rows[] |
| `DynastyBanner` | 朝代横幅，横跨三栏 | dynasty + rulers |
| `EventCard` | 单条事件卡片 | event |
| `CivBand` | 世界栏文明色带 | civilization + 位置 |
| `AxisCell` | 中轴单元（年份 + 色带 + 君主） | year + dynasty + ruler |
| `Toolbar` | 开关与筛选 | 无 |
| `RulerTable` | 世系表 | rulers[] |

### 5.3 客户端脚本

约 100 行原生 JavaScript，不引入前端框架：

- 开关切换 → 增删 CSS class
- 朝代跳转 → `scrollIntoView`
- 滚动高亮当前朝代 → `IntersectionObserver`

**渐进增强**：JavaScript 全部失效时，页面仍是一份完整可读的时间线（三栏俱在，仅开关失效）。对以阅读为主的项目，这是恰当的保证。

## 六、测试与错误处理

### 6.1 测试策略

**数据校验**是本项目最重要的质量保证。数据由 AI 生成与人工编辑混合产生，失败方式具体且可枚举，校验器能完全覆盖。本地与 CI 均执行。

**`timeline.js` 单元测试**（Vitest）覆盖边界情况：

- 朝代交替之年的归属
- 并存政权（同年多个政权）
- 跨越多年的文明色带
- 公元前后交界（不存在公元 0 年）
- 变精度日期的排序与对齐

**组件不做单元测试**：静态 HTML 渲染，问题肉眼可见，测试收益低于成本。

### 6.2 错误处理原则

- **构建时严格**：数据不合法则构建失败，绝不发布错误页面
- **运行时宽容**：可选字段缺失时该区块不渲染，页面正常工作
- **数据缺失是常态而非错误**：夏朝仅数条事件、某朝代未写概述，皆属正常。界面须体面地表现「此处尚未填充」，而非显示空白或报错

## 七、构建与部署

```
修改 YAML → git push → GitHub Actions
                        ├─ node scripts/validate.mjs
                        ├─ npx vitest run
                        └─ astro build → 部署至 GitHub Pages
```

校验失败则中止部署并报告错误位置。

## 八、第一版范围

### 包含

- **完整朝代与君主数据**：夏至 2026 全部朝代 + 历任君主
- **事件骨架**：每朝代 10–30 条，共约 300–500 条，覆盖全时段
- **抗日战争高密度样本**（1931–1945）：精确到日，约 100–150 条
- **世界事件骨架 + 文明色带**
- **长卷主页**：三栏、开关、朝代跳转、响应式
- **朝代概览页**
- **数据校验脚本 + GitHub Actions 自动部署**

### 明确推迟

| 推迟项 | 预留机制 |
|---|---|
| 全文搜索 | 内容积累后再评估 |
| 人物页 | `figures` 字段 |
| 地图 | `location` 字段 |
| 长文详情页 | `detail` 字段 |
| 农历公历换算 | 古代日期采用史料原文记法 |
| 编辑界面 | 直接编辑 YAML，配 JSON Schema 后编辑器提供补全 |

### 先做骨架而非先写透一朝的理由

若先精写秦汉，作者将长期面对一个只有秦汉的半成品，且无法验证「近现代高密度事件在此界面下是否好用」——而这恰是最需要尽早验证的部分。先打通全时段骨架并附一段高密度样本，可同时获得完整形状与密度验证。

### 成功标准

打开网页，可从夏一路滚至 2026；沿途看到每个朝代的起止、年数、开国与末代君主；滚至 1937 年 7 月 7 日可见卢沟桥事变；左栏始终有世界文明作参照。此后欲细化任何时段，只需向对应 YAML 文件添加条目。
