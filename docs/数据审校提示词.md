# 历史数据审校提示词

供外部 AI（ChatGPT / Gemini / DeepSeek 等）审校本项目数据时使用。

用法：把下面「提示词正文」整段复制给 AI，再附上要审的 YAML 文件内容。
一次审一个文件或一个朝代，不要一次丢几百条——批量越大，AI 越倾向于
笼统地说「大体正确」而不逐条核对。

---

## 提示词正文

你是历史数据审校员。下面是一份中国历史时间线项目的数据文件，格式为 YAML。
请逐条审校，**你的任务是挑错，不是确认正确**。

### 数据格式说明

日期字段为字符串，采用 ISO 8601 扩展格式，负号表示公元前，年份四位补零：

- `"-0221"` —— 公元前 221 年（仅到年）
- `"-0209-07"` —— 公元前 209 年七月（到月）
- `"1937-07-07"` —— 1937 年 7 月 7 日（到日）

其他字段：

| 字段 | 含义 |
|---|---|
| `id` | 唯一标识，不必审 |
| `title` | 事件标题 |
| `category` | 政治 / 战争 / 文化 / 科技 / 经济 / 外交 / 灾异 |
| `importance` | 1–5，5 为影响最深远者 |
| `summary` | 简述 |
| `confidence` | 确定 / 存疑 / 有争议 |
| `sources` | 出处 |
| `temple_name` | 庙号（无庙号时期存放相应称号） |
| `reign_start` / `reign_end` | 在位起止 |

### 请核对以下各项

1. **年代准确性** —— 年、月、日是否与史料相符。注意公元前年份的负号与四位补零。
2. **史实准确性** —— 事件描述、人物、地点、因果关系是否有误。
3. **君主信息** —— 庙号、姓名、在位起止、年号是否准确；开国与末代标记是否正确。
4. **`confidence` 标注是否恰当** —— 这一项尤其重要。学界本身有争议的条目却标注「确定」，是需要指出的问题。反之，早有定论的却标「有争议」，也应指出。
5. **`importance` 评级** —— 是否与该事件的历史影响相称。
6. **遗漏** —— 该时段是否缺少不应缺少的重大事件。

### 关于有争议的问题

对于学界本身存在分歧的问题（如夏商周断代、孔子生卒年、上古传说年代、
农历公历换算导致的跨年问题），**不要简单判定对错**。请说明：

- 争议点在哪里
- 主流有哪几种观点，各自的依据
- 该条目采用的是哪一种

**有几个列几个，不要为了显得全面而凑数，也不要因为不确定就略过。**

### 输出格式

以结构化列表输出，每条包括：

```
条目 id：<id>
问题类型：年代错误 / 描述错误 / confidence 标注不当 / importance 不当 / 学界争议 / 遗漏
说明：<具体问题>
建议：<修正方案，若为争议则写明各家观点>
```

**没有问题的条目不要列出。** 只列有问题或有争议的。
最后给一句总体评价：这批数据的准确度大致如何，最需要注意的是哪一类问题。

---

## 审校结果如何回填

外部 AI 给出结论后，按下列原则处理：

- **明确的年代或史实错误** —— 直接改正数据，并在 `sources` 中补上依据。
- **学界有争议者** —— 不改年代，而是把 `confidence` 调为 `有争议`，
  并在 `summary` 末尾或 `note` 中简述争议。数据的价值不在于假装
  没有争议，而在于让读者知道哪里有争议。
- **AI 之间结论冲突** —— 以有明确史料出处者为准；均无出处则标 `存疑`。
- **建议补充的事件** —— 记入待办，不必立即全部补齐。

改动后务必重跑校验：

```
npm run validate
```
