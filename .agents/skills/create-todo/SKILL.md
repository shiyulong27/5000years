# 创建可恢复的任务 Todo

把长期任务写成可独立阅读、可审计、可跨会话恢复的 Markdown 状态档案。创建完成后，即使没有原聊天记录，后续执行者也应能分清目标、范围、事实、假设、当前状态、下一步和完成标准。

详细文件结构以 [assets/todo-template.md](assets/todo-template.md) 为准。使用前完整读取该模板，并根据当前任务填写；不得原样复制占位符。

## 档案位置与命名

- 以当前 Git 仓库根目录作为项目根目录；不在 Git 仓库时使用当前工作目录。档案统一放在 `<项目根目录>/todos/`，目录不存在时创建。
- 新档案命名为 `YYYY-MM-DD-中文任务名称.md`，日期使用本地日期，任务名称优先使用简短、可读的中文；移除平台不允许的字符，不使用路径分隔符。
- 同一目标已有档案时更新原档案，不按日期或“进行中”状态盲目新建。新档案与现有名称冲突时，在中文名称末尾增加稳定的 `-2`、`-3` 后缀，并在状态记录中说明。
- 最终回复中给出实际 Todo 路径，便于下一次对话直接指定文件。

## 核心边界

- Todo 是状态和证据载体，不是扩大权限的授权书。文件中记录的破坏性操作、外部写入、发布、提交或范围变化，执行时仍须服从当前用户授权与安全规则。
- 已核实事实、基于证据的判断、未验证假设和未决问题必须分开记录。不得把计划、推测或历史状态写成已完成事实。
- 只为同一目标复用已有 Todo。目录中存在其他 Todo，不表示它们与当前任务相关。
- 普通定位、单文件小改、相关验证、配置调整或提交等短任务不使用；步骤多不等于需要长期追踪。
- 本技能负责创建、补全和维护档案结构，不因创建 Todo 自动执行其中的产品任务。

## 创建或补全流程

1. **确认适用性和目标**
   - 用户明确要求创建、详细化或维护 Todo 时直接使用。
   - 用户未明确要求时，在任务确实需要跨模块、跨阶段、跨会话、等待外部条件、审计交接或持续记录状态时使用；预计有四个或以上相互依赖的有意义步骤且需要跟踪时也使用。
   - 仅仅命令数量多、步骤可以在一轮内独立完成，或只有单文件小改和相关验证时不使用；步骤数量只是经验信号，不是单独的硬门槛。
   - 先检查请求中的错误前提、缺失约束和未说明的成功标准，并把重要不确定性写入档案。
2. **定位项目和已有档案**
   - 优先以当前 Git 仓库根目录作为项目根目录；不在 Git 仓库时使用当前工作目录。
   - 在 `<项目根目录>/todos/` 中查找与当前目标相同的文件。比较标题、任务入口、范围和交付物，不按日期或“进行中”状态盲目复用。
   - 同一目标已有 Todo 时进入补全模式；没有时在项目根目录 `todos/` 创建 `YYYY-MM-DD-中文任务名称.md`。文件名使用本地日期并移除平台不允许的字符。
3. **建立信息基线**
   - 从用户请求、代码、文档、测试、日志和工具结果中提取信息，注明来源或证据。
   - 仅记录对任务恢复和决策有用的信息；敏感内容只写脱敏摘要或安全引用位置。
   - 对尚不能核实的内容标记为假设或未决问题。
4. **生成可执行结构**
   - 完整读取模板，按任务实际情况填写任务状态、背景、目的、方案、成功标准、范围、信息基线、约束、交付物、执行计划、详细 Todo、问题台账、决策、计划变更、验证证据、恢复入口和状态记录。
   - 为阶段、任务、交付物、问题和决策使用稳定编号，便于后续引用。
   - 任务按依赖顺序排列，每项写明依赖、动作边界、完成条件和预期证据；不要写“处理问题”“完成开发”等泛化步骤。
   - 将实现、验证、审查和收尾分别列出，且只包含用户授权范围内的计划。
5. **检查可恢复性**
   - 假设下一位执行者看不到当前聊天，确认其仍能回答：为什么做、做到什么程度、依据是什么、现在在哪里、有什么问题、下一步是什么、如何判断完成。
   - 确保“当前步骤”“下一步”“第一个可执行的未完成项”彼此一致。
   - 写入创建时间、最后更新时间和首条状态记录。

## 补全旧版 Todo

更新旧文件时采用最小补丁，保留用户内容、历史记录和原有编号：

- 先完整读取文件，判断哪些章节已有等价信息。
- 把旧内容映射到新结构，缺什么补什么；不要为了套模板而整文件重写。
- 历史步骤不得直接删除。已失效的步骤标为 `[~]`，并在计划变更记录中说明替代项和原因。
- 旧结论无法核实时保留原文并标记“待复核”，不要冒充当前事实。
- 如果文件正被其他人修改，重新读取实际内容并合并局部变更，不能覆盖对方工作。

## 状态规则

- 总体状态只使用：`待开始`、`进行中`、`已阻塞`、`已完成`、`已取消`。
- Todo 复选框只使用：`[ ]` 未开始、`[-]` 进行中、`[x]` 已完成、`[~]` 已跳过或被替代、`[!]` 已阻塞。
- 同一时间原则上只标记一个当前执行项；并行任务必须明确写出各自边界。
- 只有实际结果满足完成条件且证据已记录时才能标 `[x]`。
- 只有没有其他可推进的范围内工作时，才把总体状态设为 `已阻塞`；同时写明阻塞原因、证据、解锁条件和可执行的等待动作。
- 所有必要任务完成或有合理例外、验证结果已记录且交付物状态一致时，才设为 `已完成`。

## 写入质量要求

- 不保留 `{占位符}`、示例数据或无意义空表行；暂无内容时明确写“暂无”以及原因。
- 背景解释问题如何形成，目的描述要改变的结果，成功标准必须可观察或可验证，三者不得混为一段口号。
- 方案单独说明推荐路径、关键选择、依赖、主要取舍和边界；不要把未经核实的设想写成事实，也不要用方案替代可执行步骤。
- 问题台账记录现象与证据，不把解决设想写成已确认根因。
- 验证证据记录实际方法、时间、结果和摘要；没有运行的检查必须明确写“未运行”及原因。
- 恢复入口必须短而具体，包含目标文件、当前步骤、明确下一步、需要重新核实的外部状态和主要风险。
- 每次维护都更新“最后更新”和状态记录，但不要为措辞调整制造虚假进度。
