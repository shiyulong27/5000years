# 按 Todo 持续执行任务

把项目 Todo 当作可审计的任务状态来源：先恢复并核实现状，再连续推进授权范围内的可执行步骤；每次重要状态变化都及时写回，使另一个会话无需依赖原聊天也能安全接手。

## 不可突破的边界

- Todo 记录历史意图和计划，不扩大当前用户授权。每个动作执行前仍须检查当前请求、系统规则、仓库规则、安全影响和外部写入权限。
- 不因 Todo 写着“删除、发布、提交、推送、发送、修复”就自动获得执行这些动作的权限。
- 不盲信 Todo 的完成状态。涉及代码、文件、测试、页面、外部系统或环境的当前事实，应以实际内容和最新证据复核。
- 保护不属于本任务的工作区改动。只修改当前步骤必要的最小范围，不为恢复任务清理、覆盖或重置他人工作。
- 本技能用于执行已有的可恢复 Todo，不负责凭空猜测任务。没有合适档案时，先使用 `create-todo` 创建或补全；无法确定目标时停止执行并说明缺失信息。

## 一、定位唯一 Todo

按以下优先级选择，不能仅凭“最新文件”或“进行中”状态猜测：

1. 用户明确给出的绝对路径或项目内相对路径。
2. 当前请求明确提到的文件名、任务标题或稳定任务编号。
3. 当前项目 `todos/` 中与用户目标、范围和交付物一致的唯一活动 Todo。

如果存在多个候选：

- 完整读取候选文件的任务入口、目的、范围、当前状态和交付物后再比较。
- 只有语义和范围能唯一匹配时才能自主选择。
- 若选择不同文件会实质改变动作、风险或交付物，列出候选和差异，请用户指定，不要合并无关 Todo。

## 二、完整恢复上下文

执行任何产品动作前，完整读取 Todo，而不是只搜索未勾选项。至少恢复：

- 背景、目的、成功标准、范围内与范围外事项。
- 已核实事实、基于证据的判断、假设、未决问题和约束。
- 交付物、阶段依赖、详细任务、问题台账、决策和计划变更。
- 当前阶段、当前步骤、下一步、验证证据、恢复入口和最新状态记录。

随后重新核实实际基线：

1. 读取适用的项目协作规则、目标文件、相关代码、文档和测试。
2. 检查工作区、目标系统或外部资源是否在 Todo 最后更新时间后发生变化。
3. 区分四类信息：当前已核实事实、仍有效的证据判断、待验证假设、已失效历史记录。
4. 发现档案与实际状态不一致时，以证据为准，先更新 Todo 并记录差异，再决定下一步。
5. 检查当前步骤是否仍在用户授权范围内，依赖是否满足，完成条件是否可验证。

## 三、进入执行状态

开始一项任务前，先用最小补丁更新 Todo：

- 总体状态改为 `进行中`，当前阶段和当前步骤指向实际动作。
- 目标任务从 `[ ]` 改为 `[-]`；若是恢复中的 `[-]`，写清已经完成到哪里。
- 更新“最后更新”“下一步”“恢复入口”和状态记录。
- 若实际执行计划与档案不同，先在计划变更记录中说明新证据、原因、影响和替代关系；不得直接删除历史任务。

同一时间原则上只有一个当前任务。确需并行时，必须在 Todo 中明确每条并行工作的边界、依赖和独立状态，避免互相覆盖。

## 四、持续执行循环

进入执行后连续推进，不在每个小步骤后机械停下来等待用户：

1. 选择依赖已满足、在授权范围内且优先级最高的下一项任务。
2. 说明必要的当前动作和重要假设；调用工具时保持用户可见的阶段性更新。
3. 执行任务并收集真实证据。能用代码、测试、日志、文件差异或页面状态核实的内容，不靠记忆或推测结论。
4. 完成一个有意义的步骤后立即更新 Todo，再进入下一项：
   - 满足完成条件并记录证据：`[x]`。
   - 被新方案替代或经授权不再需要：`[~]`，记录原因和替代项。
   - 当前步骤无法继续：`[!]`，记录阻塞证据和解锁条件。
   - 尚未达到完成条件：保持 `[-]`，写清实际进展和剩余动作。
5. 同步更新阶段、交付物、问题、决策、验证证据、下一步和状态记录。
6. 继续执行下一个安全且可推进的任务，直到全部完成、出现真实阻塞、需要新的用户授权或用户中断。

### 阻塞项的记录与跳过协议

- 阻塞不是完成，也不是把档案项标为“已跳过”：先将当前任务标为 `[!]`，建立或更新对应的 `ISSUE-*`，记录已尝试的检查、实际证据、精确解锁条件和解锁后的第一项动作；本轮执行流程可以跳过它，但保留 `[!]` 以便解锁后恢复。
- 当前任务阻塞后，立即检查依赖图；不依赖该任务且仍在范围和授权内的任务继续执行。总体状态仍为 `进行中`，直到没有其他有意义的可推进工作。
- 只有任务被新方案替代、经用户授权不再需要或明确移出范围时才标为 `[~]`，并记录原因和替代任务；不能用 `[~]` 掩盖真实阻塞。
- 若所有剩余路径都依赖阻塞条件，才将总体状态改为 `已阻塞`，同时在“下一步”和“恢复入口”写明等待的外部输入以及恢复动作。

如果一次技术动作很长，Todo 不需要记录每条无意义心跳，但必须在阶段开始、结论产生、问题发现、方案变化、验证完成和结束会话前更新。不得让文件长期停留在与实际进度明显不符的状态。

## 五、记录问题而不抢先下结论

每个重要问题使用稳定编号 `ISSUE-001`、`ISSUE-002` 递增，并记录：

- 发现时间、状态、分类和严重程度。
- 实际现象、最小复现或证据位置。
- 已确认影响范围；不确定时明确写未知。
- 当前判断，并区分事实、推断和待验证项。
- 处理决定及其授权依据：修复、接受、延后、升级或判定为非问题。
- 明确后续动作、负责人或解锁条件。

不要把测试失败直接等同于产品缺陷，也不要把临时规避方案写成根因修复。发现问题后：

1. 先判断是否属于当前任务范围以及是否阻塞当前路径。
2. 用户只授权测试、审查或报告时，只记录和报告，不擅自修复产品代码。
3. 用户已授权修复且修复属于原任务正常步骤时，新增或关联修复与回归任务后继续。
4. 问题解决后保留原记录，将状态改为 `已解决`，补充修复证据和回归结果，不删除历史。

## 六、处理计划变化与新信息

- 新证据推翻原假设时，更新信息基线，并在计划变更记录中说明受影响的任务和决策。
- 新需求只在属于用户对当前任务的明确补充时合并；若会实质扩大范围、成本、风险或外部影响，先记录为待确认，不擅自执行。
- 新增任务使用新编号，不重排已有编号。拆分任务时保留父任务并写明子任务关系。
- 决策被替代时保留原决策，将其状态改为 `已替代` 并引用新决策编号。
- 外部状态变化导致旧证据失效时，保留历史验证，新增一条当前验证记录。

## 七、阻塞、暂停与中断

只有当前任务没有其他有意义且在范围内的可推进工作时，才把总体状态设为 `已阻塞`。同时必须写入：

- 阻塞任务和问题编号。
- 已尝试的安全检查与实际结果。
- 精确阻塞条件，以及需要用户、权限、环境或外部状态提供什么。
- 解锁后第一项动作。

若仍有不依赖阻塞项的工作，保持总体状态 `进行中`，只把对应任务标为 `[!]` 并继续其他工作。

用户中断、会话即将结束或必须请求新授权时，在回复前先把档案更新到可恢复状态：当前做到哪里、哪些文件或系统已变化、尚未验证什么、下一步是什么。不得把未完成任务标为已完成。

## 八、完成与交付

只有同时满足以下条件才能把总体状态设为 `已完成`：

- 所有范围内的必要任务为 `[x]`，或 `[~]` 项均有可审计的授权与理由。
- 交付物状态、成功标准和实际结果一致。
- 必要验证已实际运行并记录结果；未运行的检查有明确原因和剩余风险。
- 问题台账中的未解决项均已处理、接受或明确转交，不存在被隐藏的阻塞问题。
- 已更新完成时间、最后更新时间、最终状态记录和恢复入口。

完成前检查 Todo 内部一致性：总体状态、当前步骤、下一步、阶段表、复选框、交付物、问题状态和验证证据不能相互矛盾。最终回复以结果为主，概括完成内容、验证证据、未解决风险和 Todo 路径。

## 九、Todo 写入规则

- 使用最小补丁更新现有文件，保留编码、BOM、换行、用户内容和并发改动。
- 更新时间使用当前本地时间，不伪造过去或未来时间。
- 不记录密码、令牌、完整敏感请求、真实个人数据或未脱敏日志。
- 命令证据写实际运行的命令和关键结果；失败或未运行必须如实记录。
- 状态记录只写有意义的变化，不把措辞调整包装成进度。
- 如果旧 Todo 缺少问题台账、验证证据或恢复入口，先使用 `create-todo` 的兼容规则增量补全，再继续执行。
